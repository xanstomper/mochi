build.js is the trajectory export CLI: `node build.js <trace.jsonl> <runId> <out.json>`. Today it just wraps the raw trace entries in a { runId, exportedAt, entries } dump — nothing downstream (dashboards, SFT data prep, failure analysis) can consume that. Replace it with a structured TrajectoryRecord builder. Create trajectory.js exporting buildTrajectory(entries, meta) — entries = parsed trace JSONL objects (each with numeric t and a kind), meta = { runId } — and rewire the CLI to write buildTrajectory's result. The record contract:
- Top level: { schemaVersion: 1, runId, startedAt, endedAt, durationMs, task, steps, outcome, usage, failureTaxonomy }. startedAt = the FIRST entry's t (null when no entries/stamp), endedAt = the LAST entry's t, durationMs = max(0, endedAt − startedAt), 0 when either stamp is missing.
- task: from the FIRST task:started entry — its task payload as a bare string becomes { title }; as an object becomes {} plus title (when a non-empty string) and prompt from its description (when a non-empty string); a task:started with no usable payload yields {}; no task:started at all yields null.
- outcome: the LAST task:completed/task:failed entry wins — { completed: true, stopReason? } for completion (no reason), { completed: false, stopReason?, reason? } for failure (reason stringified when present); { completed: false } when there is no terminal entry.
- steps: tool:called opens a step { index, tool, args (null when absent), ok: false, outputSnippet: '' }; the next tool:completed/tool:failed for the SAME tool closes the oldest still-open step for that tool. On completion: outputSnippet = the result's text capped at 500 chars — the result itself when a bare string, its .output when an object ('' when that is missing; fall back to the entry's own output field when there is no result), coerced with String() when needed. On failure: outputSnippet '' and error = String(the entry's error) ONLY when one was recorded (no invented default). durationMs: the completion result's numeric durationMs when present, otherwise derived as completion t − call t; the key is absent when neither exists. A completion/failure with no open call becomes its own step with args: null. A call that never closes stays ok: false with no error key.
- usage: sum numeric fields from usage:updated entries (the entry itself) AND any entry's nested usage object, accepting both namings (inputTokens|promptTokens, outputTokens|completionTokens, cacheTokens|cachedTokens, totalTokens, costUsd; first matching alias per source record). The record's usage contains ONLY the fields actually seen, and is null when no usage numbers appear anywhere.
- failureTaxonomy: [{ label, count }] in this order — stopReason labels: 'tool_loop', 'verification_failed', 'stuck_no_progress' (count 1, only when the outcome stopReason equals or contains the label; arbitrary stopReasons are NOT labels); 'repeated_tool_calls' = number of (tool + JSON-identical args) groups among tool:called ENTRIES with ≥3 calls; 'tool_errors' = count of tool:failed entries, or when there are none, the number of not-ok steps carrying an error.
Verify against the fixtures in traces/: run-ok (clean two-tool run, object task, flat usage), run-loop (string task, three identical calls, a tool failure, tool_loop ending), run-messy (orphan completion, unclosed call, over-long output, no task/usage/terminal entry).
