plan-gate.js decides plan-mode batches for the agent loop: decidePlanBatch(calls, config) returns which tool calls execute (runIds), which are vetoed (vetoedIds), and whether the batch ticks the plan-mode veto counter (vetoCounted). Today every mutating call is vetoed — including a POST to the project's own local dev server or an internal read-only API, which a codebase-aware agent legitimately needs to READ while planning. There is no way to declare "calls to this host are exploration, not mutation".

Add an operator-declared network-read allowlist, config key safety.planModeNetworkReads (an array of hostnames):
1. A mutating fetch call (per isFetchMutationRequest from fetch-methods.js — POST/PUT/PATCH/DELETE) whose URL hostname is declared executes in plan mode like a read. Tool names are canonicalized through the alias map first, so an alias spelling of fetch earns the same treatment as 'fetch' itself.
2. Matching is EXACT hostname equality — the URL's hostname (port excluded) — compared case-insensitively. No substring, suffix, or superstring matching: declaring 'ost' must not bless 'localhost', declaring 'localhost.evil.com' must not bless 'localhost', and declaring 'example.com' must not bless 'api.example.com'.
3. Non-fetch mutating calls (writes, edits, shell) are never exempted, and a fetch with an unparseable URL fails closed (vetoed).
4. Only actual refusals count: vetoCounted is true exactly when at least one call in the batch was vetoed. An exempted call executes and never ticks the counter; a batch whose only mutating call is exempt does not count.
5. Every call id still lands in exactly one of runIds/vetoedIds, batch order preserved. An empty or absent allowlist changes nothing, and GET/HEAD fetches keep running as before without needing any declaration.
